# Postmortem: Search API 500 Errors (Issue #60)

**Date**: 2026-02-06
**Duration**: Unknown (detected by user report, likely since build `pax-vault-build-2026-02-06-002`)
**Severity**: P2 — Search broken (region + pax), rest of app functional
**Status**: Resolved
**GitHub**: https://github.com/F3-Nation/pax-vault/issues/60

## Summary

`/api/region/list?q=<term>` and `/api/pax/list?q=<term>` returned HTTP 500. BigQuery could not find views `pv_regions` and `pv_events` because the `@google-cloud/bigquery` SDK resolved the dataset location to `us-central1` (the Cloud Run instance's region) instead of `US` (the dataset's actual multi-region location). The search routes also lacked error handling, so any BQ failure became an unhandled 500.

## Impact

- All region and pax search queries returned 500
- Non-search pages (pax stats, region stats, AO stats) were unaffected — they happened to resolve the correct location via auto-detection in different code paths
- No data loss or security exposure
- Reported by @taterhead247 in Slack

## Root Cause

**Primary**: The BigQuery client in `src/lib/db.ts` did not specify a `location` parameter. The `@google-cloud/bigquery` SDK defaults to auto-detecting the location, which resolved to the Cloud Run instance's own region (`us-central1`) rather than the dataset's actual location (`US` multi-region). BigQuery returned `Not found: Table f3data:public.pv_regions was not found in location us-central1`.

**Secondary**: The search API routes (`/api/region/list`, `/api/pax/list`) had no try-catch around the BigQuery call. Any query failure propagated as an unhandled exception, producing a raw HTTP 500 with no logging.

## Error Evidence

From prod logs (`pax-vault/.context/issues/2026-02-06-issue60-500-err-in-search/logs.json`):

- 3x HTTP 500 on `/api/region/list?q=<term>` (queries: "Princeton" x2, "jocoga" x1)
- `Error: Not found: Table f3data:public.pv_regions was not found in location us-central1`
- `Error fetching Region data: Error: Not found: Table f3data:public.pv_events was not found in location us-central1`
- Latency on 500s: 323-422ms
- All from same revision `pax-vault-build-2026-02-06-002`

## Resolution

### 1. Added `location` to BigQuery client (`src/lib/db.ts`)

Read `BIGQUERY_LOCATION` env var (defaulting to `"US"`) and pass it to the `BigQuery` constructor so all queries resolve against the correct dataset location.

### 2. Added `BIGQUERY_LOCATION=US` to env files

- `.env.local`
- `.env.firebase`

### 3. Added error handling to search API routes

Wrapped BQ calls in try-catch in both `/api/region/list/route.ts` and `/api/pax/list/route.ts`. On failure, logs the error and returns `[]` with HTTP 200 instead of an unhandled 500.

## Lessons Learned

### What went wrong

1. **No explicit BigQuery location**: The SDK's auto-detection is unreliable when the Cloud Run instance region differs from the dataset's multi-region. This should have been set from the start.

2. **No error handling on search routes**: The search endpoints were the only API routes without try-catch. A single BQ error surfaced as an opaque 500 to the user with no server-side logging.

3. **Non-search routes were unaffected**: This masked the location mismatch during initial deployment testing — pax/region/AO detail pages worked fine, so the issue only appeared when someone triggered a search.

### What went right

1. User reported the issue quickly with a screenshot
2. Prod logs clearly identified the exact BQ error and location mismatch
3. Fix was straightforward — env var + error handling, no schema or infrastructure changes
